# Wyoming–Halogen implementation plan

## Goal

Build a standalone proxy that discovers the speech models hosted by a configured Halogen server and exposes their supported speech-to-text (STT) and text-to-speech (TTS) capabilities through Wyoming. Home Assistant and other Wyoming clients should be able to discover and use these services without knowing Halogen's HTTP API.

## Scope and technology

- Use Python with asyncio, the upstream `wyoming` package for event parsing and TCP serving, and an asynchronous HTTP client such as `httpx` for Halogen.
- Connect to one configurable Halogen base URL initially; no inference runs inside the proxy.
- Serve STT and TTS on one configurable Wyoming TCP listener. Advertise only capabilities actually discovered and supported by the adapter.
- Support buffered STT and streamed PCM TTS first. Wake words, conversational inference, model installation, voice cloning, and streaming text input are outside the initial scope.
- Supply a Python CLI and container image. The proxy requires no GPU or NPU access.

## Required Home Assistant outcome

Home Assistant integration is the primary release requirement. The user must be able to run this proxy, connect it through Home Assistant's built-in Wyoming Protocol integration, and select its STT and TTS providers in an Assist pipeline. No custom Home Assistant integration should be required.

The documented setup must cover:

1. Start Halogen with supported speech models and start the proxy with a LAN-accessible TCP listener.
2. In Home Assistant, add the Wyoming Protocol integration using the proxy's hostname/IP and port, as described in the [official integration documentation](https://www.home-assistant.io/integrations/wyoming/).
3. Verify that both STT and TTS providers are created when both capabilities are available.
4. Configure a voice assistant pipeline with these providers, a compatible language, and a supported TTS voice; retain the user's chosen conversation agent.
5. Speak a command through Assist and verify transcription, command handling, and audible speech generated by Halogen.

Validate how Home Assistant presents model and voice choices rather than assuming every Wyoming model becomes a separately selectable entity. If Home Assistant cannot select individual STT models, provide configurable per-model listener instances/ports so each desired model can be added as a separate Wyoming integration entry. Document the same option for independently selectable TTS models if needed.

Also test integration reload/reconnection after proxy restart and model inventory changes. A refreshed Wyoming description alone does not guarantee Home Assistant updates its entities immediately; document any required reload. Automatic network discovery and a Home Assistant app package can follow later; manual host/port setup must work in the first release.

## Upstream contracts and initial investigation

The repository currently contains only a README. Before implementing adapters, pin tested upstream versions and capture representative `/health` and `/v1/models` responses from Halogen with no speech models, STT only, TTS only, and both enabled.

Halogen documents `/health` as the authority for the running build's capabilities, while `/v1/models` includes hosted NPU models. Speech endpoints are `/v1/audio/transcriptions` and `/v1/audio/speech`. Optional authentication uses a bearer token; health remains public. See the [API reference](https://github.com/peonist-ai/halogen-flash-server/blob/main/docs/api.md).

Confirm the exact model metadata fields, readiness semantics, language metadata, multipart transcription contract, and cancellation behavior against that pinned build. Do not assume the full OpenAI API contract applies. Keep saved fixtures and record any fields unavailable for discovery.

## Architecture

Separate the implementation into these modules:

- `config`: CLI/environment configuration and validation.
- `halogen`: reusable HTTP client, authentication, discovery, transcription, and speech requests.
- `registry`: immutable snapshots of discovered models and capability metadata.
- `profiles`: verified model-family contracts, language mappings, voices, and audio formats.
- `audio`: PCM validation, WAV wrapping, format conversion, and aligned output chunking.
- `server`: Wyoming connection lifecycle and per-connection request state.
- `stt` and `tts`: request translation and response handling.

Share the HTTP pool and model registry across connections; isolate request state and audio buffers per connection. Bound active requests and queued work so concurrent clients cannot exhaust memory or overload Halogen.

## Model discovery and Wyoming descriptions

1. Fetch `/health` and authenticated `/v1/models` on startup with bounded timeouts.
2. Classify models using explicit capability and route metadata where available. Audio input/output modalities alone do not prove that a model implements the dedicated speech endpoints.
3. Where upstream metadata is insufficient, use a tested model profile for recognized IDs. Provide explicit configuration overrides for custom IDs, capabilities, languages, voices, and formats. Avoid broad name substring guesses or inference calls during routine discovery.
4. Store exact upstream IDs, STT/TTS support, readiness evidence, languages, speakers, attribution, format constraints, and metadata provenance. One model may support both STT and TTS.
5. Translate snapshots into Wyoming `info` on `describe`: STT appears under `asr`, synthesis under `tts`. Populate required fields using upstream metadata or verified profiles; do not invent languages, attribution, or readiness. Require overrides when required metadata cannot be established.
6. Use stable advertised names and retain an explicit mapping to upstream IDs. Sort deterministically. Advertise speakers using the model's supported voice IDs.
7. Refresh periodically and atomically replace snapshots. On failure, record degraded health and expire stale capabilities after a configurable grace period. A successful empty inventory removes speech services immediately. Recovery requires no restart.
8. Pin the selected model and its profile for each in-flight request. Refreshes affect subsequent requests; disappearance upstream produces a clear request failure.

Initial profiles should cover discovered Qwen3-ASR and Qwen3-TTS CustomVoice variants. Evaluate LFM3-Audio and LFM3-Omni separately because their language and voice contracts differ; expose them only after endpoint compatibility is verified. The [Halogen NPU reference](https://github.com/peonist-ai/halogen-flash-server/blob/main/docs/NPU.md) documents these families and their speech contracts.

Model selection must be deterministic: honor an explicit Wyoming selection, otherwise use a configured default, otherwise select the sole compatible model. Reject ambiguous selections and unavailable models. Verify the upstream Wyoming library's STT selection fields before choosing an extension; document how clients that cannot select an STT model use the configured default.

## STT translation

1. Accept Wyoming `transcribe`, then `audio-start`, zero or more `audio-chunk` events, and `audio-stop`, following the upstream event contract.
2. Validate event order and PCM metadata, consistent chunk formats, sample alignment, maximum duration, and maximum bytes. Clear state after completion, error, or disconnect.
3. Buffer bounded audio until `audio-stop`; wrap PCM as WAV and convert only when required by the selected profile. Choose and document a maintained resampling implementation after verifying accepted upstream formats.
4. Send the model ID, WAV file, and optional normalized language to `/v1/audio/transcriptions` using its verified multipart contract. Request a supported response format and translate the result to Wyoming `transcript`.
5. Preserve an empty successful transcript as empty text. Distinguish silence from malformed input and upstream failure.

The initial service returns a final transcript and does not advertise transcript streaming. Verify whether external VAD is required and set Wyoming capability flags accordingly.

## TTS translation

1. Accept Wyoming `synthesize`; resolve its voice/model/speaker fields against the advertised registry and validate language and text limits.
2. Send `model`, `input`, the mapped `voice`, and supported language options to `/v1/audio/speech`.
3. For profiles verified to support it, request `response_format: pcm` with `stream: true`. Qwen3-TTS currently documents 24 kHz, 16-bit mono PCM. Keep format metadata per profile rather than assuming it for every model.
4. Emit Wyoming `audio-start` with the actual format, then aligned `audio-chunk` events as bytes arrive, followed by `audio-stop` only after successful completion. Retain partial samples across HTTP chunks and reject a truncated final sample.
5. Support a verified WAV fallback by parsing the container and forwarding decoded PCM, never WAV headers. Apply response-size limits and backpressure.
6. Enforce per-model voices, languages, and text limits. Initially reject oversized text with an actionable error; automatic sentence splitting can follow later.

Streaming generated audio does not imply support for Wyoming's streaming text-input synthesis events; advertise that flag as false initially.

## Configuration and operations

- Configure listener URI, Halogen URL, optional API-key environment variable or secret file, discovery interval, stale grace period, connection/request timeouts, request concurrency, audio/text limits, default models/voice, and metadata overrides.
- Default to a loopback listener; document an explicit LAN binding for Home Assistant. Wyoming is intended for trusted networks and has no native authentication or encryption; see its [security model](https://github.com/OHF-Voice/wyoming/blob/main/SECURITY.md).
- Keep the Wyoming listener available during upstream outages so discovery can recover. Return empty capability lists when no usable inventory exists and report degraded status through logs and an explicit health command.
- Translate HTTP authentication failures, missing models, invalid input, busy responses, timeouts, and malformed responses into stable Wyoming error events supported by the pinned library. Do not silently retry inference after audio has been emitted.
- Cancel upstream work on disconnect, release buffers, close HTTP streams, and drain/cancel tasks on shutdown.
- Log discovery changes, request type/model, elapsed time, and failures. Never log keys, raw audio, or transcript/synthesis text by default.

## Validation and acceptance criteria

Use fixture-based unit tests for discovery/profile mapping and audio conversion, plus socket-level Wyoming integration tests against a mock HTTP backend. Cover fragmented HTTP audio, malformed event sequences, format mismatches, oversized requests, upstream errors, concurrent connections, disconnects, and repeated requests on a persistent connection.

The first release is complete when:

- Only discovered, compatible speech models appear in `info`; unrelated language, embedding, and image models never appear as STT/TTS.
- Adding or removing a hosted model changes subsequent descriptions within the configured refresh interval, without restarting the proxy.
- A Wyoming recording produces the expected Halogen transcript, with language and model selection honored.
- Synthesis produces valid PCM with the selected voice and correct Wyoming audio framing.
- STT-only, TTS-only, no-model, authentication-failure, outage, and recovery cases behave predictably.
- Limits, concurrent clients, cancellation, and shutdown leave no unbounded buffers or orphaned requests.
- A documented Home Assistant setup completes an end-to-end voice interaction.
- Home Assistant exposes usable STT and TTS providers through its built-in Wyoming integration, and the user can select the intended hosted models (directly or through configured model-specific listeners).
